# Tasks：完成后的活动清单清理

## 当前行为与根因

`src/tasks/index.ts` 的完成反馈经过 5 秒后隐藏 Dock 完成组，不删除 TaskStore 数据；`src/tasks/model.ts` 新增仍向同一 tasks 数组追加，nextId/nextChild 继续递增。默认 task_list 只查 unfinished，不等于已完成记录已清除。

组完成状态和进度由子项派生。立即删除一个 done 子项会改变总数/比例；删除全部子项留下的空组不是 done。现有 delete 同时移除被删除 ID 的依赖边；历史/存活 child 的 assigned 与恢复又依赖原清单和任务身份，不能只在 UI 删除一行或计时器到期后无条件删存储。

## 可行策略与建议

先明确清理粒度：单项 done 即清理、整组 done 后清理、或全部完成后轮换活动清单。建议优先以完成组或整清单为边界，不在部分完成时抹掉子项进度。

“清理当前任务”建议先定义为退役活动清单：完成记录不参与默认查询、Dock 或新任务组织，新增进入新的活动组织；仍需保存的完成记录在同一 TaskStore 内保留历史/只读身份，不另建平行任务存储。物理删除可作为明确的 owner 清理操作，单独确认其不可恢复影响。

编号建议继续递增：即使清空活动清单也不复用同会话 ID。不把 nextId/nextChild 重置为 1；如果要求新清单重新编号，必须有 epoch/batch 身份并贯穿 task、依赖、child/job 引用和授权，避免旧执行写到同名新任务。这是更大的协议改动，不是单纯清空数组。

清理由清单 owner 在 TaskStore 原子事务内处理，包含依赖和完成回执；assigned child 的 done 不能隐式获得删除父组/兄弟的权限。UI 计时器仅呈现真实完成 5 秒反馈，不承担持久清理；恢复不重放反馈，旧 Store/Binding 回调不能作用于新清单。任务完成不停止 job/child，也不等于 Goal 完成。

历史任务退役后的显式重新打开/child resume，需要定义原引用继续可读和重新变为活动的授权，不能通过删除记录让恢复入口无意失效。

## 待确认与任务

- [ ] 确认只退出活动清单并保留历史，还是自动永久删除；建议先退役活动清单。
- [ ] 确认编号继续递增还是需要带 epoch 的重新编号；建议不复用 ID。
- [ ] 定义依赖、assigned、历史恢复/重新打开、空组和部分完成的行为。
- [ ] 在 Store 锁内实现并验证清理与并发新增的竞态、fork 完整计数器及 5 秒反馈，不以 UI 定时器做 GC。
