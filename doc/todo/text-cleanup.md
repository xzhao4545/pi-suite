# 文本整理

## 目标

清理项目中的描述性文本，使其准确、易读、无重复。范围：

- `doc/current` 全部文档。
- 模型可见文本：工具与参数描述、错误信息、注入给模型的说明与通知正文。
- UI 文本：按键提示、状态行、标签、通知。
- 源码注释：只改失真、空话或复述代码的注释，不逐行重写。
- `doc/todo` 下未完成的计划文档。

`docs/`、README 与两个技能文件已单独重写，不在本范围；本次修改造成的事实变化需同步到这些文件。

## 现有问题

- 术语堆砌：用内部抽象名代替具体机制，例如"执行归属""控制代次""准入""承载"，读者需要先懂实现才能读懂文档。
- 长句串联多个条件，一段话同时讲状态、边界、例外和验证。
- 同一规则在多个页面重复定义，各处措辞不同，部分已互相矛盾。
- 混入修改记录、验证流水、"不再……""继续……"等描述历史的字句，违反 `doc/current` 只写当前状态的规则。
- `validation.md` 记录了大量验证过程和专项编号，而 `doc/current` 只应保留验证结论、适用范围和未通过项。
- 模型可见文本过长或把内部许可模型直接写给模型，例如 goal 注入规则让模型误以为用户轮不能工作。

## 写作标准

- 先写结论，再写条件。一句话一个意思。
- 写具体机制、数字和来源；不用自造术语。必须使用的内部名（类名、字段名）写成代码格式，并在首次出现时说明它是什么。
- 每条规则只在一处定义，其他位置链接。
- 只写当前状态，不写"已改为""不再""旧版"等历史字句；历史细节已在 `doc/finished`。
- 表格用于并列的字段、状态或按键；流程用编号步骤。
- 模型可见文本：只写模型做决定所需的内容（何时用、参数、返回、失败时怎么办），不写内部实现和许可机制；错误信息说明原因和下一步。
- UI 文本：不写功能需求说明（AGENTS.md 规则），短标签优先。
- 每个文件改写后，事实必须与源码一致；无法确认的事实标注并上报，不删除。

## 执行方式

- 按模块目录分批，每批同时处理该模块的 `doc/current` 页面、模型可见文本、UI 文本和注释。
- 每批改写前核对源码；改动字符串后运行该模块相关测试，测试断言字符串时同步更新断言。
- goal 模块在 [Goal 暂停与用户轮](./goal-pause.md) 的代码完成后处理。
- 允许按文件重写，前提是保留全部当前事实；完成后 AGENTS.md 的文档规则不变。

## 验收

- 每个文件符合写作标准；无修改记录和验证流水。
- 链接与锚点检查通过；typecheck 与全量测试通过。
- 受影响的 `docs/` 中英文与 README 同步。
