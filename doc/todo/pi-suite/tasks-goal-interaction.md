# Tasks 展示、更新与 Goal 控制优化

状态：需求与方案已记录，以下实现和验收均未完成。本专项覆盖任务常驻区、任务工具、`/tasks` 浏览器及主模型的取消/恢复行为。

## 原始需求

- [ ] 1. tasks 常驻显示改为清晰的 `#数字 标题`；优化当前运行中图标，参考 oh-my-pi（OMP）的设计。
- [ ] 2. tasks 更新不以普通工具调用的详细参数和返回值铺开，简短显示哪个任务完成、开始或阻塞，研究 OMP 的实际呈现方式。
- [ ] 3. 减少 tasks 更新工具需要输入的参数，参考 OMP 的操作协议。
- [ ] 4. 修复任务更新后，输入框附近的任务状态没有变化的问题。
- [ ] 5. 重新设计 `/tasks` 的任务列表，使列表与详情更清楚、美观。
- [ ] 6. 定位模型输出时按 Esc 仅看到 goal 暂停、输出未中断的问题，保证取消作用于实际运行。
- [ ] 7. 优化输出期间执行 `/goal resume` 的行为，解释并修正不必要的“待恢复”状态。

Suite 需要保留两级结构、稳定短 ID、多个执行任务并发、TaskStore 的串行/原子提交。OMP 的完整标题匹配、init 全量替换、单一进行中项和标题推测执行归属不适合直接照搬；Suite 已有明确 taskId 与执行引用。

## 1. 常驻任务区

### 当前问题

`src/tasks/index.ts` 拼接父级的完成比例、todo/doing 和 blocked 文本，子任务用 `▶/!/✓` 前缀。展示和状态文案直接混在行构建里，缺少统一的任务呈现规则。

共享 Dock 优先保留各组摘要，之后才分配子任务行；组较多时，正在变化的执行任务可能完全不显示。父级派生状态也可能在子任务变更后保持 doing，用户难以看出发生了什么。

### 修改建议

- 左侧固定为 `#ID 标题`，子任务仅保留轻量缩进，状态移到右侧；父级右侧显示完成比例。
- 进行中使用主题强调色及 `⟳`，完成使用 `✓` 与弱化/删除线，阻塞使用 warning 色及 `⚠`，待办使用弱化色。颜色之外保留符号，让状态可辨认。
- 示例中的图标是 Suite 的拟议样式；OMP todo 本身使用复选框，不将这些图标描述为其原样设计。
- 当前执行任务、阻塞任务与最近完成项应在任务区预算内得到可见反馈；多组时使用其余组摘要和隐藏数量。若调整父子行预算，应扩展共享 Dock 行分配契约，避免 tasks 单独绕过总高度预算。
- 保留最近完成项的短暂反馈；常驻区、工具摘要与浏览器从同一 TaskView 和状态规则生成展示。

示意，实际使用主题颜色：

```text
#1 登录流程优化                    1/3
  #2 检查请求链路                    ✓
  #3 修复状态同步                    ⟳
  #4 回归验证                        ⚠
```

## 2. 更新工具的简短反馈

### 已确认原因

`src/tasks/tools.ts` 中 task_list 和 task_edit 均未注册 renderCall/renderResult，因此宿主使用通用工具展示。task_edit 返回操作、JSON 字段、父级状态、警告与查询提示，形成大段技术文本。

### 修改建议

- 使用 Pi 原生工具渲染接口，调用中显示“正在更新任务”，成功后默认只展示实际变化；展开才显示变更字段、组进度与依赖详情。
- 原子提交回执带上稳定 ID、对应标题、前后状态及必要原因；删除项的标题从提交前数据取得。重复设置相同状态不能重复报“刚完成”。
- 同批多项默认显示简短摘要与有限变化行；创建清单展示组名、数量与简短预览。task_list 默认显示简洁清单，查询详情仍可展开。
- 警告、失败和未提交必须可见，不能将失败渲染成成功。模型侧保留必要结构化结果和真实工具结果，不另发聊天消息伪装成工具执行。
- OMP 的合并与同轮替换部分属于其宿主能力。先使用当前 Pi 的 renderer/context 能力完成紧凑展示；如宿主不支持替换，保留简短历史，不自行改写会话或建立另一套工具面板。

拟议默认结果：

```text
✓ #2 检查请求链路 · 已完成
⟳ #3 修复状态同步 · 已开始
⚠ #4 回归验证 · 已阻塞：等待服务恢复
```

## 3. 工具参数与阻塞语义

### 当前问题

更新一个状态必须写 changes 数组、update 操作及 status 字段。当前只有 todo/doing/done，blockedBy 表示依赖阻塞，不能表达 OMP 那种“等待用户/服务、注明原因”的手动阻塞。

### 修改建议

task_edit 支持顶层单操作，日常进度使用 start/done/block/unblock；add/update/delete 处理创建和通用字段变更。批量继续用 changes，且仍在同一个 TaskStore 事务内提交，不拆成逐项工具执行。顶层单操作与批量入口互斥，schema 和执行校验使用统一操作契约。

```json
{"changes":[{"op":"update","id":"2","status":"done"}]}
```

拟议单项与批量参数：

```json
{"op":"done","id":"2"}
{"op":"start","id":"3"}
{"op":"block","id":"4","reason":"等待服务恢复"}
{"op":"unblock","id":"4"}
{"op":"add","title":"登录流程优化","children":["检查请求链路","修复状态同步","回归验证"]}
{"changes":[{"op":"done","id":"2"},{"op":"start","id":"3"}]}
```

- 继续用短 ID，不要求模型重复完整标题；不添加字符串缩写 DSL 或含糊的位置索引。
- 增加明确的手动 blocked 状态与可选原因；依赖阻塞仍由 blockedBy 派生。显示层统一计算有效阻塞及原因，手动解除不得清掉尚未完成的依赖。
- 约定 unblock 将手动 blocked 任务返回 todo；完成任务不因批量 block 重新打开；父级进度与状态由统一模型派生。具体父级阻塞规则、持久 schema 升级及完成依赖的行为随实现一并明确。
- 保留并发执行，不按 OMP 的 start 操作自动把其他 doing 任务降回 todo；不隐式完成整个 goal。
- 调整模型工具说明，要求只发送有变化的字段，状态更新与后续实际工作尽可能同轮调用，减少纯任务更新的模型往返。

## 4. 输入框附近状态同步

### 已确认与待定位边界

当前单进程链路为 `TaskStore.mutate → listeners → TasksModule.refresh → Dock.invalidate`，同进程 child 共享父级 TaskStore。已有 UI 测试覆盖此链路，因此不能直接归因为“忘了刷新”。

JsonStore.snapshot 从文件加载后不广播变化，且没有跨进程文件订阅；外部进程写入同一任务文件不能主动通知本进程。与此同时，多组摘要占满 Dock 或父级派生状态未变也会导致变化不可见。用户实际触发的是哪条路径仍需确认。

### 修改建议

- 先确认用户所指是输入框上方 Dock，还是其他组件，以及写入来自主模型、同进程 child 或其他 Pi 进程；核对真实 store target、绑定与 UI 可见行。
- 先验证单任务变化后的数据、订阅事件和最终渲染是否一致，再处理渲染预算，保证提交后对应变化能被看到。
- `/tasks` 当前刻意使用打开时快照，需与常驻区的更新问题区分。浏览器改为订阅规范状态后，不再等待关闭重开才能看到更新。
- 若确认跨进程写入是支持场景，变化检测与发布回到统一存储层；有订阅者时观察所属文件目录中的原子 rename，加载成功且数据实际变化后发布事件，解绑时释放。不要在每次渲染读文件或为 tasks 开永久高频轮询。
- 不在工具结果里再维护一份 UI 任务缓存；读取、变更、执行引用与 UI 均使用同一规范状态来源，加载失败明确提示。

## 5. `/tasks` 浏览器

`src/tasks/viewer.ts` 默认将 taskDetails 的描述、依赖、agent/jobs 引用全量铺开，正文为打开时快照，操作栏含 Expand/collapse 与 Show/hide completed。

建议复用 `src/ui/browser.ts` 的 BrowserView 和原生 SelectList：顶部组范围、状态与输入筛选；左侧列表只展示 `#ID 标题`、组进度和小状态符号；右侧显示所选任务的状态、描述、阻塞原因/依赖及执行引用。筛选应覆盖编号、标题和描述，组进度始终统计所有子任务。

```text
Tasks
组: [全部] 登录流程优化
状态: [未完成] 全部  进行中  阻塞  完成
Filter: 同步

#3 修复状态同步              ⟳ │ #3 修复状态同步
                               │ 状态：进行中
                               │ 所属：#1 登录流程优化
                               │ 描述：更新后立即刷新任务区
                               │ 依赖：#2 检查请求链路（已完成）
                               │ 执行：subagent / job 引用
```

只保留一套状态筛选，不再叠加 Show/hide completed。复用共享焦点、滚动、搜索与窄终端上下布局；通过稳定 ID 保存选择与每条详情阅读位置。状态更新可刷新记录和计数，但不无故跳选或重置滚动；所选项退出筛选时再确定相邻选择。浏览期间继续使用统一通知 hold，关闭后恢复交付。

## 6. Esc 与真实取消

### 当前证据

当前安装的 Pi 与项目依赖均为 1.5.0。suite 没有注册 Esc 快捷键或终端输入拦截。Pi 默认编辑器在主模型 streaming 时通过 restoreQueuedMessagesToEditor 调用 session.abort；ExtensionContext.abort 也接入宿主取消路径。

suite 在 aborted 结算后停止 goal 自动续跑：目标仍为 active、调度变为 idle、automatic=false。当前摘要显示 `⏳ goal`；显式 `/goal pause` 才设置 paused 并显示 `⏸ goal`。因此“按 Esc 变为暂停但继续输出”与当前默认源码链路不完全吻合，尚不能认定具体根因。已有 goal 测试直接调用 session.abort，没有覆盖真实键盘焦点与按键路径。

用户补充复现条件：焦点在输入框，按 Esc 后主模型仍正常输出正文和思考。该现象应按主模型流未停止排查；是否存在补全状态、取消后重新接纳的运行或 Provider 流未响应取消，还需实际追踪确认。

### 修改建议

- 从真实 TUI 复现按键 → 编辑器/补全/详情焦点 → 宿主 abort → Provider AbortSignal → 停止正文/思考增量 → 最终结算，区分持续新输出与取消前已到达的少量缓冲。
- 使用最小扩展组合与用户当前组合对照，排查取消事件被菜单、编辑器或其他扩展截获，以及宿主/Provider 未停止读取的实际位置。
- 修正在宿主取消链路或统一 goal 生命周期中的确切问题，不用仅修改 goal 图标的方式声称中断成功，也不新增抢占所有 Esc 的并行快捷键。
- 若 goal 使用暂停图标表达 Esc 后的停止续跑，应同步定义其自动许可与调度语义，防止图标误报仍在运行的主响应。独立后台 jobs/subagents 的停止仍按执行归属处理，不将 Esc 扩大为停止所有后台任务。

## 7. `/goal resume` 的恢复与等待

### 已确认原因

`GoalManager.resume()` 无条件设置 active/automatic=true，并将 schedule 改为 idle，再经 Notifications 排队。即使同一 goal 的响应正在 running，也会失去运行标记并显示等待。

Notifications 只有在当前会话 idle、无待处理消息、无查看器 hold 且允许唤醒时才立即交付；busy 时在合适结算边界合并后续工作。等待当前响应、取消收尾或压缩完成有实际原因，不能另开第二条并发主模型请求。

### 修改建议

- 同一 goal 已在正常运行：resume 幂等，保持 `🎯 goal`，不创建重复续跑请求。
- 已暂停且宿主真正 idle：恢复自动工作许可，由统一协调器立即接纳一次继续。
- 宿主正在取消收尾、压缩、其他响应或查看器 hold：记录实际等待原因，状态栏显示等待图标，`/goal` 详情与命令反馈解释原因；条件解除后只恢复一次。
- 验证 Esc 与 resume 的交错，避免较早响应的 aborted 结算覆盖用户较新的恢复意图；复用目标 ID、修订号、绑定及运行归属边界管理该顺序。
- resume 默认表示继续目标，不强行中断其他主响应；若未来需要“中断并重启当前响应”，应使用有明确语义的独立动作。

## 实施顺序与验收

先处理 Esc 的真实取消、resume 状态转换与任务同步，再完善 blocked 模型和紧凑参数，最后统一常驻区、工具渲染及浏览器。

- 取消/恢复：真实按键能够停止主模型新增输出；文本、思考与工具等待分别明确取消边界；重复 resume 不启动重复请求，busy/idle 切换和取消交错不丢恢复意图。
- 状态同步：主模型与同进程 child 提交后立即更新规范状态和可见反馈；仅在确认支持跨进程同清单后补充该同步契约；多组、小高度与长标题不隐藏所有进度反馈。
- 工具协议：单项参数简短，批量仍原子提交；手动阻塞与依赖阻塞可区分；失败可见，多执行任务仍可并发，不用全量清单覆盖并发修改。
- 展示：常驻区和默认工具结果简洁；`/tasks` 可筛选、查看详情与跟随更新，宽窄终端可用，稳定选择和阅读位置保持一致。
- 实施时仅为取消/恢复交错、共享存储状态同步和原子协议等明确风险添加必要验证；图标与小文案调整不单独增加固定回归条目。
