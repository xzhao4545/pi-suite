# Goal 上下文与自动续跑优化

## 状态与目标

本项为待实施方案。第一阶段解决完整 Goal 合同重复进入模型上下文和动态状态过期；第二阶段独立增加轻量无进展停跑。阶段完成后才能将对应稳定行为写入 `doc/current`，不能把本方案描述成已经生效的实现。

总体方向：保留进程内 GoalManager、现有状态机、持久快照、运行归属和统一调度框架，分离稳定执行规则、当前 Goal 合同和自动续跑信号。

目标是让模型每次请求只获得一份当前有效合同，Goal 自身的重复控制开销不随自动续跑次数增长；不是限制正常用户消息、模型输出、工具证据和真实后台事件的增长。

## 一、问题与根因

### 1. 当前 Goal 对象与历史消息不是同一层

当前 `Goal.text` 只有显式编辑时变化，`usedTokens`、`turns` 等为数值累加；`progress` 在等待、阻塞或完成时覆盖，不是每轮追加的执行日志。因此，内存 Goal 对象没有自动积累完整工作历史。

`GoalManager.save()` 将完整状态保存为 `pi-suite:goal` 自定义条目。普通 `custom` 状态条目不直接参与模型上下文，持久快照承担分支恢复、清除记录、许可元数据和审计职责。每秒 UI 时钟也不追加状态记录、不触发模型请求。

本项不将状态快照的磁盘增长与模型指令增长混为一谈。

### 2. 完整合同被当作每轮续跑消息

`goalContract()` 当前同时生成目标正文、ID/revision、状态、进度、预算与错误，以及完成审计、阻塞、等待和用户同意规则。`GoalManager.request()` 将这份完整合同放入 Notifications；送达后形成新的 `pi-suite:notification` 自定义消息并进入模型历史。

稳定请求 ID `goal:<ID>` 只覆盖尚未送达的 pending 队列项，不替换已经写入会话的历史消息。因此，同一目标连续续跑仍反复追加完整合同。

真实 SDK 离线验证、关闭压缩、使用短英文目标时，第 1/5/20 次请求中的完整 Goal 通知分别为 1/5/20 份，累计文本为 839/4208/16853 字符。这些值只证明重复累积的形态，不是生产 tokenizer、费用或缓存效果的基准；系统合同、工具定义与工具结果也不包含在这些字符数中。

### 3. 系统合同不一定跟随底层请求刷新

当前 `before_agent_start` 注入 `pi-suite-goal` 系统提示节；自动续跑可通过 `agent_before_settle` 和 `agent.continue()` 留在同一高层运行中，不重新触发 `before_agent_start`。

已核对的离线执行中，第 20 次请求的系统合同仍写 `Tokens: 0`，当前 Goal 账本已有累计用量，而后续通知携带新数字。运行时预算判断仍由代码执行，但模型同时看到旧系统快照、旧通知和新通知。

必须分别处理账本更新、请求级合同更新、历史控制消息淘汰，不能用“每次多追加一份新系统消息”修复状态新鲜度。

### 4. 通用压缩只能缓解

compaction 可以缩短较早历史，但反复复制合同仍会在两次压缩之间占用上下文、挤占工具证据，并增加压缩负担。压缩不会使原始持久历史停止追加，也不是 Goal 专用去重机制。

## 二、范围与不变约束

### 必做范围

- 拆分稳定执行规则、当前合同和续跑信号。
- 在每次底层模型请求前，根据当前运行归属投影最新合同。
- 自动续跑不再把整份合同放进通知。
- 为新生成的 Goal 控制片段保留明确来源，安全控制其模型上下文占用。
- 验证重试、压缩、编辑、取消、会话恢复和后台通知不回归。

### 保留的能力

- 目标状态与调度状态分离，不增加平行状态机。
- `automatic`、`resumeRequired` 和显式恢复许可。
- `stop` 保留目标、`clear` 删除当前目标的区别。
- `goalId + revision + Binding + controlRevision + AbortSignal` 运行归属。
- 完整状态快照、分支恢复及冷启动许可撤销。
- Notifications 的队列去重、准入、宿主忙闲判断和用户输入优先级。
- WaitRegistry 的对象结算、提问、monitor/update 与期限唤醒能力。
- StatusPublisher、共用详情查看器与不落盘的 UI 时钟。
- 完成审计、幂等完成和用户同意边界。

### 本项不做

- 不重写 GoalManager、会话持久化或工具注册框架。
- 不新增独立进程、独立控制服务或第二套续跑队列。
- 不更换预算口径、不新增默认预算、不把 token 使用量等同费用。
- 不增加重试、租约、熔断、完成判定分类器等子系统。
- 不修改源 JSONL，不根据文本相似度清洗用户历史。
- 不在 Goal 合同中自动复制完整 tasks/todo 历史。
- 不照搬上游长续跑模板；参考职责分离与调度边界，不复制重复指令方式。

## 三、目标数据流

```text
命令 / Goal 工具 / 生命周期事件
             │
             ▼
       同一个 GoalManager
       ├─ 当前状态、归属、执行许可
       ├─ custom 快照 → 会话恢复 / 详情 / 审计
       ├─ 短续跑信号 → Notifications → 宿主继续边界
       └─ 请求级只读视图 → Pi 上下文钩子 → 一份有效 Goal 合同

真实 job / agent / workflow 事件 → Notifications → 正常事件内容
稳定执行规则 → 独立提示节，不随用量反复复制
```

状态、日志、调度和模型视图保持各自职责。请求投影读取当前内存状态，不另建模型专用的持久 Goal 状态，不把提示文本反向解析为执行授权。

## 四、第一阶段设计

### 1. 拆分提示职责

| 内容 | 应包含 | 不应包含 | 更新方式 |
| --- | --- | --- | --- |
| 稳定执行规则 | 不得缩小目标、逐项验证、权限模式、同意边界、完成/阻塞/等待原则 | 当前目标正文、用量、进度、错误 | 独立提示节；同样规则不反复追加 |
| 当前 Goal 合同 | ID、revision、目标正文、当前状态与本轮权限、预算、用量、进度、必要错误/等待原因 | 全部历史进度、每轮审计全文、重复参数范围 | 每次请求按当前状态生成 |
| 续跑信号 | 继续当前目标、以本次有效合同为准 | 目标正文、预算快照、审计全文 | 经统一通知框架送达，保持简短 |

工具 schema 已表达的参数范围、错误码或长描述不在合同中完整复述；影响模型决定的关键原则仍需保留。精简不得削弱验证范围、目标完整性或同意要求。

`progress` 继续是当前记录，不自动改造成工作日志。长目标继续遵守现有长度约束并允许引用文件，不静默截断限制或验收条件。

### 2. 高层运行准入与请求级投影分开

`before_agent_start` 继续负责判定本轮是否接纳 Goal、建立执行或仅结案归属，并设置稳定规则，不再负责动态用量的唯一刷新。

使用 Pi 公开的 `context_with_system` 请求级钩子处理完整提示视图；需要处理纯会话控制片段时使用公开 `context` 钩子。两者都不替代持久更新入口。

请求级合同的处理顺序：

1. 检查当前运行与所选会话 Binding、Goal ID、revision 和控制代次是否仍匹配；沿用现有归属事实，不重复构造另一套许可。
2. 对已接纳的运行读取最新状态和本轮权限，生成一份合同。
3. 只处理本模块拥有的 Goal 提示节，避免本模块旧合同与新合同同时作为有效控制指令送达。
4. 将本次合同放入请求投影视图，不为每个模型请求追加持久合同消息。
5. 未接纳、已取消或过期运行不得获得新执行许可；本模块历史提示不应继续表现为仍有效的自动执行授权。

具体提示节名称及放置位置在实施时确定，但必须同时满足最新值、模块隔离、宿主提示回放和 provider 缓存边界。不以强制替换整个系统提示实现局部更新。

### 3. 提示投影边界

- 保留 leading system message、其他扩展提示节以及工具声明与增删记录。
- 不删除整条系统消息来清除其中一个 Goal 节；消息可能还携带其他提示或工具元数据。
- 不改变工具注册、活动工具集或 executable 权限。
- 不把其他模块消息折叠成 Goal 内容，也不重排真实用户指令与工具结果。
- 目标正文和文件内容属于用户任务数据，与框架规则分开；遵循结构化渲染/转义边界，不让包装文本变成新的框架授权。
- 保持宿主及其他扩展的 chained transformation 顺序，核对强制提示投影是否覆盖本模块输出；不允许合同静默丢失。
- 对支持中途提示更新的 provider，保留稳定前缀；对折叠系统消息的 provider，使用公共 adapter 能力验证最终有效提示。
- 不承诺所有 provider 零缓存失效，不通过写 provider 私有 payload 绕过公共框架。

### 4. 续跑通知只表示唤醒

`GoalManager.request()` 继续使用 `goal:<ID>` 请求 ID 和 Notifications，但只提交简短、可识别的 Goal 续跑控制内容。模型应从本次有效合同读取 ID、revision、目标、预算和进度，而不是从唤醒消息读取完整快照。

继续保留这些调度规则：

- 待发送同 ID 项覆盖，不重复排队。
- 已有宿主继续或待处理消息优先，不多启动主模型。
- error/aborted 不由短消息强行续跑。
- 宿主忙于取消、压缩或重试时保留恢复意图，等可用边界统一处理。
- paused/stopped 等状态、用户等待与 waitFor 准入仍约束通知送达。
- 详情阅读和 UI 时钟不触发执行。

不能把 Goal 改成直接在 `agent_end` 发 prompt；`agent_end` 不是最终 idle 边界。

### 5. 在现有 Notifications 中保留来源

现有通知框架需要能够区分 Goal 控制片段和真实事件，而不只是把全部正文拼成不可分辨的字符串。使用最小必要的结构化来源信息；具体采用独立 customType 或混合通知分段元数据，在实现时依据统一送达接口选择，不同时维护两套协议。

来源应支持区分：

- Goal 自动续跑控制。
- job 结算、monitor 或 hands-free 更新。
- agent 结果或直接 child 提问。
- workflow 结果及其他真实通知。

无论最终序列化是一条还是多条消息，都必须保持一次送达、一次唤醒及既有回调语义，不能因拆分内容触发两个模型运行。

请求投影只保留当前执行所需的最近 Goal 续跑控制内容，其他真实事件原样保留。不因预算数字不同将 Goal 控制片段认定为新的工作证据。

### 6. 历史与恢复边界

以下内容不能作为可删除的重复控制片段：

- 用户真正输入的目标、补充要求、修改和停止指令。
- 模型执行内容、文件读取、命令输出和工具结果。
- 完成证据、阻塞证据和真实外部事件。

已写入日志的新控制消息可保留审计来源，但模型视图中的重复控制开销应保持有界。保留执行所需的末尾续跑上下文，核对宿主 `canContinue` 和 provider 请求实际可执行性；不能去重后把继续请求变成无有效上下文的请求。

既有会话中未带结构化来源的混合通知不进行全文正则清洗、不整条删除、不改写原始日志。它们由正常 compaction 逐步处理。新协议的有界性验收与历史遗留内容分别记录，不用旧会话残留否定新协议，也不宣称旧副本已被自动全部移除。

会话切换、树导航、编辑和清除后，根据当前 Binding 与状态重新投影。历史快照只是恢复材料，不是绕过 `resumeRequired` 的授权。

## 五、必须保持的生命周期合同

| 操作/事件 | 必须保持的行为 |
| --- | --- |
| 创建目标 | 新 ID，清零用量和有效时长，开启自动工作 |
| 编辑目标正文 | 保留 ID、revision 增加，原修订归属调用失效，取消原 job 等待并中止旧运行 |
| 编辑预算 | 保留累计用量；达到上限限制；提高上限后显式 resume |
| pause | 保留目标，撤销自动许可，取消 Goal 唤醒与等待，中止归属运行 |
| stop | 保留目标、progress、error、用量、时长和 stoppedFrom；中止归属运行 |
| clear | 删除当前目标并中止归属运行，不把历史文本当成新的执行许可 |
| resume | 校验预算，显式恢复许可，清除等待及相关错误/停止字段，不重复启动主模型 |
| 输入框 Esc | 保留 active，停止自动续跑；按现有新用户输入或 resume 规则恢复 |
| ask_user | skipped/timed_out 不提供同意授权；cancelled 保留明确用户等待及恢复要求 |
| goal_wait | 等待已安排事件，冻结有效 running 时长，按 WaitRegistry 或期限恢复 |
| provider 重试 | 复用宿主重试，等最终结算，不另加 Goal 重试 |
| compact | 成功按宿主边界恢复；失败/取消停止自动工作；已有等待保持 |
| quit/冷启动 | 未完成目标要求手动恢复；树导航/reload 不绕过许可撤销 |
| complete | 逐项验证，保留原证据和完成时间，重复完成幂等 |
| 非 active 用户审计 | 可取得仅结案权限，不恢复 automatic、不授予 wait/block 执行权限 |
| 后台工作 | Goal 停止不等于递归停止全部 jobs/subagents/workflows；保留各自控制边界 |

“仅结案权限”是 Goal 工具和调度权限，不自动等同只读文件沙箱。完成证据真实性与同一障碍连续三轮不能被描述为由参数校验自动证明。

## 六、第二阶段：轻量无进展停跑

### 1. 独立实施

先完成第一阶段并确认生命周期不回归，再增加无进展检测。检测只影响自动 Goal continuation，不把普通用户轮或每个底层工具响应当成独立无进展轮。

候选信号为连续自动轮没有工具活动、或相邻自动轮工具调用与结果完全相同；真实等待走现有 `goal_wait`。需要在实施前确定自动轮边界、阈值及误伤控制，不直接把上游实现当成默认规则。

### 2. 最小状态与控制行为

命中停跑条件时保留 Goal 为 active，撤销 `automatic`，取消 pending Goal 唤醒，冻结运行时长，并保存明确的自动停跑原因。原因通过既有详情与通知展示，提示显式 `/goal resume`。

- 不自动 complete，不把未完成工作改称成功。
- 不借用 blocked 表示无活动，不伪造外部障碍。
- 不将停跑原因混写为 provider error。
- 不新建独立暂停状态机；必要的原因字段并入现有状态模型。
- 显式 resume 重新开始检测；编辑、替换、Binding 撤销不继承另一执行阶段的检测结果。
- 恢复后的旧结算不能覆盖新恢复意图。
- 停跑后的后台通知不得偷偷恢复 automatic；用户输入是否恢复应明确写入操作合同并验收，不能偶然依赖回调顺序。

### 3. 检测局限

没有工具不必然没有进展，推理、研究和文档任务可能暂时只输出文本；工具输出变化也不证明工作有效。因此不新增完成分类器，不扫描整个历史，不把活动摘要当成任务质量判据。

如使用工具活动摘要，只记录必要的当前/上一自动轮信息，避免保留完整工具输出或每轮累计摘要数组。正常变化的输出、确有意义的只读验证与真实等待需要通过典型任务确定处理方式。

## 七、预算、持久化与性能

### 1. 预算不在本项改口径

继续使用宿主 `totalTokens`，包含输入、输出和缓存用量；仅结案审计继续计入用量。文档应说明这是累计 token 使用口径，不等于实际费用。新增工作量或费用预算另行形成独立需求，不与提示重构同时改变。

### 2. 状态持久化不重建

保留 `pi-suite:goal` 完整快照、最后分支记录恢复和跨分支许可元数据。只对有明确证据的同节点相同快照重复保存进行局部合并，不增加增量日志、缓存层或数据库。

请求级合同从内存状态生成，不写入一份新持久 snapshot。UI tick 不承担合同更新，不增加模型请求或磁盘写入。

### 3. 性能要求

- 每次请求不重新读取或扫描 JSONL，不为获得当前 Goal 重新遍历全会话。
- 控制片段来源按 metadata/type 判定，不扫描工具结果正文或完整 notification 文本。
- 公共上下文钩子中只做必要的模块级变换，避免重复完整序列化会话和工具定义。
- 不因用量变化强制重建整个 leading system prompt。
- 正常请求转换的成本应随宿主已有上下文遍历保持线性，不增加嵌套全历史比较。
- 字符数、tokenizer、缓存命中和费用分别说明；不使用离线估算冒充真实 provider 计费。

## 八、实施步骤与文件范围

| 阶段 | 工作 | 主要位置 |
| --- | --- | --- |
| 第一阶段 A | 拆分规则、当前合同、续跑内容；明确任务数据边界 | `src/goal/state.ts`，必要时新增聚焦提示模块 |
| 第一阶段 B | 请求级合同投影；高层准入保留 | `src/goal/index.ts`、GoalManager 的只读归属视图 |
| 第一阶段 C | request 改为短控制信号 | `src/goal/manager.ts` |
| 第一阶段 D | 来源信息与安全去重，保持真实通知和一次唤醒 | `src/runtime/notifications.ts`，公共消息边界 |
| 第一阶段 E | 真实 SDK 验证、provider 投影、当前文档同步 | `tests/goal`、公共通知相关用例、`doc/current/goal` |
| 第二阶段 | 自动轮活动边界、停跑原因、恢复重置与验证 | `src/goal/manager.ts`、`state.ts`、操作文档 |

## 九、验收标准

### 1. 上下文有界

用真实 SDK 离线 provider、关闭压缩，覆盖连续自动续跑与同一高层运行的多次底层请求。

- 本模块当前有效 Goal 合同只有一份。
- 新协议生成的完整目标正文/合同副本不随自动轮次累积。
- 模型中的重复 Goal 控制内容保持有界；允许最新数字位数等自然变化。
- 用户指令、模型输出、工具结果和真实后台事件正常保留。
- 原始审计日志增长与模型视图去重分别检查，不用 UI 隐藏代替模型投影证明。

### 2. 最新状态与归属

- 下一底层请求显示最新 usedTokens、预算、progress、状态、等待原因及本轮权限。
- 文本修改后的下一有效运行取得新 revision；旧请求不会取得新修订执行或完成权限。
- 仅结案轮保留精确 ID 及权限，预算耗尽不被投影自动恢复。
- 暂停、清除、取消、换分支后的历史控制文本不授予自动执行。

### 3. 通知与宿主边界

- Goal/job/agent/workflow 混合通知不丢结果、提问或指定更新。
- 一个送达批次不因拆分片段触发两次请求。
- 用户输入和已存在的宿主继续保持优先级。
- 去重后宿主继续上下文仍可执行，不能只有队列“已送达”而 provider 没有有效触发材料。
- 真实等待仍按指定对象、期限、monitor/update 或直接 child 提问恢复。

### 4. 提示和 provider 边界

- 其他模块提示节、leading system message 与工具声明保持完整。
- 公开提示回放结果中的当前 Goal 正确，不单凭 `ctx.getSystemPrompt()` 的高层视图判定请求已更新。
- 覆盖中途提示更新与折叠系统提示的代表性 adapter 路径。
- 核对强制提示与扩展顺序，不允许合同静默丢失或被重复注入。
- 有费用/缓存结论时注明真实测量范围；离线验证只声明协议与内容结论。

### 5. 第二阶段停跑

- 空活动或重复活动按明确阈值停止自动续跑，不修改为完成/阻塞。
- 用户主动轮、有效工具证据、正常等待和典型只读研究不被错误分类。
- resume/编辑/替换/会话切换正确重置检测，旧结算不覆盖新意图。
- 停跑原因可查看、可恢复、可持久化；后台通知不能绕过恢复要求。

### 6. 验证规模

优先扩展已有真实宿主与归属测试，新增用例只覆盖上下文投影、通知混合和自动轮停跑等跨模块高风险合同，不为每个提示字符串添加测试。日常测试保持 5 分钟内，全量保持 10 分钟内；不新增长期测试产物或本机产物归档清单。
