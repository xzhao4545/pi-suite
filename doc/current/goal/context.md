# 请求上下文与自动续跑

## 状态来源

当前目标文件（见 [存储](storage.md)）是目标状态的唯一来源。`GoalManager` 在每次运行开始时读取它并决定本轮权限（见 [本轮权限](lifecycle.md#本轮权限)）。模型历史里的目标说明、会话快照和摘要都不能恢复状态或授予权限。

## 注入给模型的目标说明

目标说明以持久会话消息的形式追加（`display: false`，不在界面显示），由 `src/goal/context.ts` 生成：

| 消息 | 何时追加 | 内容 |
| --- | --- | --- |
| `pi-suite:goal-context` | 模型可见的历史中没有当前目标与 `revision` 的完整说明时 | 规则正文，以及 `goalId`、`revision`、`control`、`access`、`budget`、`status` 和完整目标正文 |
| `pi-suite:goal-control` | 上述字段（目标正文除外）相对最近一条目标消息有变化时 | 只有变化后的字段 JSON |

字段都未变化时不追加。用量、响应次数、耗时、进度与诊断只保存在状态文件和界面里，不写进模型上下文。工具的证据与等待要求写在各工具描述中。目标正文不截断。

规则正文告诉模型：做完并验证每一条原始要求，不得换成更容易的目标；最新的目标消息取代较早的；`access` 为 `execute` 时目标自动续跑，可用 `goal_wait`、`goal_blocked`；为 `complete` 时目标不会自行继续，照常处理用户消息，所有要求都已验证时才调用 `goal_complete`，需要自动续跑由用户执行 `/goal resume`；`ask_user` 的 skipped、timed_out、cancelled 结果不代表同意。

### 与宿主提示的关系

- 目标模块不在 `context` 钩子里过滤历史，不替换历史末尾，不改系统提示，也不改 Provider 请求体。较早的目标消息保留在历史中，语义由最新一条覆盖。
- Pi 1.5.0 在两种上下文钩子之后应用强制系统提示，并把系统节合并到新的开头。目标说明是会话消息，不受这一步影响。
- 已发送的历史前缀保持不变，只在末尾追加，便于 Provider 的前缀缓存。本地用真实 Responses 序列化器核对过：正常续跑保留整个前次 input 前缀以及系统、工具与缓存键。实际命中率取决于服务端，不作保证。
- 压缩会移除旧的目标说明。压缩后从当前状态补发：普通启动通过 `before_agent_start` 返回；压缩重试与工具之间的阈值压缩通过宿主 steering，在宿主已安排的下一次请求前送达。补发说明不会为此唤醒已完成或正在等待的目标。
- 只在启动和压缩这两个时机检查宿主的模型视图（`buildSessionProjection`），不逐请求扫描会话文件。

## 自动续跑请求

自动继续通过公共 Notifications 投递，请求 ID 固定为 `goal:<ID>`，未送达的请求会合并。

- 继续请求只是一句简短的唤醒（`Continue the current goal.`），不复制目标正文、预算、进度或审计内容。
- 只有目标继续的批次不在界面显示。与 job、agent、workflow 等真实事件合并的批次使用事件正文，不另加继续文本；目标的送达回调仍只执行一次。
- 宿主已有的继续、待处理消息、用户输入、取消、重试、压缩和等待优先。一个送达批次只唤醒一次。
- 暂停、完成、clear、修改目标或撤销绑定只取消尚未送达的请求，不删除已经发送的历史。

`pi-suite:notification` 消息的正文由文本块组成。`details.notificationVersion` 为 1，`details.segments` 与正文块一一对应，记录每块的 `requestId` 和 `source`：`goal-continuation`、`event`，或不唤醒模型的 `reminder`。事件的具体来源由 `requestId` 区分，`details` 不重复保存正文。Tasks 提醒也使用这种消息，在自然的 `turn_end` 追加且不请求继续，频率见 [任务提醒](../tasks/operations.md#提醒)。

`/goal resume` 成功后保存一条可见的 `pi-suite:goal-resume` 条目，`data.summary` 与 `data.text` 只有一行结果。该条目不进入模型上下文，也不触发请求。命令在共享通知暂停期间写入条目，然后才放行继续请求。完整状态用 `/goal status` 查看。

## 自动停跑

自动停跑防止模型在无人值守时空转。

- **自动轮**：从一次目标继续请求实际送达开始，到宿主最终完成、准备安排下一次继续时结束。同一轮里的工具往返和宿主重试不另计。出错的尝试不结束自动轮，也不计为无工具轮；`agent_before_settle` 遇到错误、已有 `continue` 或待处理消息时先等宿主处理，不重复安排继续。
- **比较内容**：每次工具调用的名称与参数，以及最终 content、details、structuredContent 与是否出错，各自取摘要（含嵌套调用），按调用发起的顺序比较。调用 ID、耗时与宿主用量不参与比较，不保存完整输出。
- **触发**：连续 5 个自动轮没有任何工具调用（`no_tools`），或连续 5 个自动轮的调用与结果摘要完全相同（`repeated_tools`），目标暂停并显示通知 `Goal paused · no tool activity` 或 `Goal paused · repeated tool activity`。这不是完成、外部阻塞或请求错误。
- **恢复**：用户的新消息或 `/goal resume` 恢复自动续跑并清零计数。后台通知、`/reload`、树切换和压缩不会恢复。
- **计数清零**：用户发起的运行、真正进入 `goal_wait`、修改或替换目标、撤销绑定、非重复的 resume。旧控制下的结算不能停掉更新后的恢复。

这个保护只看是否有工具活动，不评估工作质量，也不会自动完成目标。纯文本推理也可能有进展，但连续超过阈值后仍需要用户确认再继续。
