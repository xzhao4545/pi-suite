# Tasks：完成后的活动清单清理

## 分析时的行为与根因

`src/tasks/index.ts` 的完成反馈经过 5 秒后隐藏 Dock 完成组，不删除 TaskStore 数据；`src/tasks/model.ts` 新增仍向同一 tasks 数组追加，nextId/nextChild 继续递增。默认 task_list 只查 unfinished，不等于已完成记录已清除。

组完成状态和进度由子项派生。立即删除一个 done 子项会改变总数/比例；删除全部子项留下的空组不是 done。现有 delete 同时移除被删除 ID 的依赖边；历史/存活 child 的 assigned 与恢复又依赖原清单和任务身份，不能只在 UI 删除一行或计时器到期后无条件删存储。

## 用户确认与清空方案

用户已确认：全部完成后清空活动清单，不保留任务历史，清空后完全重新开始；还需提供模型主动清空入口。无需逐个完成项或完成组退役，不保留历史活动/归档清单。

在现有 task_edit 增加 owner 级 clear 操作，由清单 owner 在 TaskStore 锁内原子删除当前任务、依赖和执行关联；全部非空任务完成时通过同一清空路径自动处理。clear 与 done 的回执保留必要的完成/清空结果，不回传已删除的完整任务。assigned child 不能借 clear 删除父级或兄弟任务；私有清单的 owner 可清空自己的清单。

用户已明确授权清空后从 1 重新编号：重置 nextId/nextChild 的同时轮换清单 epoch/generation，并贯穿工具和已捕获执行引用，避免旧执行写到同名新任务。该代次只用于权限与过期引用校验，不保存旧任务内容或历史。存量记录的迁移、缺少代次的旧执行与恢复路径也不能静默绑定新清单。

清空不停止 job/child，也不完成 Goal；旧任务关联失效时给出明确错误，不自动重新分配同名新任务。清空后的历史 child 恢复不得假装原 assigned 任务仍存在，需由 owner 显式建立新的任务关联。

用户已明确授权首次启用时清空当前会话已全部完成的存量清单。不扫描其他会话或工作区，也不为了初始化或 fork 清理而修改持久 fork 的源清单。

UI 计时器仅呈现真实完成 5 秒反馈，不承担持久清理。实际任务清空后反馈使用必要的短期显示信息，恢复不重放反馈，旧 Store/Binding 回调不能作用于新清单。
