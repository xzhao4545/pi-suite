# 启动性能优化

- [x] 测量不加载扩展与加载扩展时的启动差值，定位扩展导入、模块创建、会话绑定各阶段耗时。
- [x] 按实测贡献消除重复读取和扫描，推迟不影响启动契约的重依赖加载。
- [x] 同时验证首次命令/工具调用、reload 和会话切换，保证优化后的功能就绪与生命周期正确。

## 目标与当前状态

用户反馈：使用本扩展后启动速度需要优化。目标是缩短从启动 Pi 到输入、命令、工具和补全可用的等待，并降低扩展带来的额外耗时。已完成真实资源加载路径的新进程对照测量，优化注册与执行加载边界、首次配置读取和类型快照共享；具体数字与适用范围见下方验收结论。

## 已确认的初始化工作

| 路径 | 当前行为 | 优化方向 |
| --- | --- | --- |
| `src/index.ts` 静态导入 | 入口直接导入所有模块、查看器和 workflow；关闭模块不免除其导入链成本。jobs 的 Manager 又静态导入 PTY 后端，连接 `zigpty`、`@xterm/headless` 和序列化组件；workflow runtime 连接 Worker 源码等依赖 | 测量实际加载/转换成本，按现有模块边界拆分必要注册和按需执行/查看依赖 |
| 首次配置读取 | `createSuite` 调用 `loadConfig`，紧接着首次 `bindSession` 再次读取；workflow 冲突检查另外读取原始配置以判断显式启用 | 首次准入与绑定共享同一配置快照，保留字段来源/显式配置事实；之后按 cwd 和激活边界重新读取 |
| 类型发现 | 默认启用 workflow 与 mentions 时，`workflowTool.bind → refreshTypes` 和 `mentions.bind → loadTypes` 各自调用 `agentTypes`，重复发现、读取及解析相同资源 | 同一绑定内共享一次目录快照，供工具说明、补全和类型入口使用 |
| 包资源解析 | 每次 `agentTypes` 经 `packageResources` 新建 `SettingsManager` / `DefaultPackageManager`，枚举配置包、读取 manifest，并进行文件系统解析 | 复用 Pi 公开资源/包能力；确需扩展时统一在既有 catalog/resources 层完成，不绕过信任与包开关 |
| 关闭 mentions 的绑定 | `mentions.bind` 在检查 TUI 模式之前调用 `loadTypes`，也没有先按 `agents.mentions` 跳过类型读取 | 关闭该能力或无需该补全时省去专属工作；其他类型使用者仍按自己的实际需求发现资源 |
| 会话初始化 | `bindSession` 顺序等待 tasks 快照、恢复 agents/jobs/workflow、更新 workflow 类型说明、读取并处理 schedules，随后绑定 mentions/RPC 和刷新通知 | 分阶段测量并明确依赖；只并行独立 I/O，保留状态绑定和准入顺序 |

入口中的配置 schema 还通过 `thinkingSchema` 导入完整 catalog，catalog 再连接包解析代码。即使推迟模块实例创建，公共配置的导入链也需一并评估；可将共享 schema 放到现有轻量数据定义边界，避免为一个枚举加载整套发现能力。

## 测量与实施方案

1. 使用真实 Pi 扩展加载路径测量，区分 TypeScript 加载/转换、factory 注册、首次 `session_start`、首次可交互和首次使用。测试辅助代码直接导入 factory 的结果只能说明 SDK 初始化成本，不能代替实际 CLI 加载结论。
2. 在相同设备、cwd、配置、其他扩展和会话数据下，对比扩展关闭、默认开启、全部业务模块关闭，以及有实际资源/历史的场景。分别测量新进程与 `/reload`；固定预热方式，多次取样记录中位数和变化范围，排除模型网络请求影响。阶段计时使用临时或可关闭的开发诊断，不在正常启动展示日志。
3. 先合并已确认的重复配置读取和 catalog 扫描，使用本次绑定的共享快照；按实测再决定重依赖的按需导入。Types 修改、资源变化后的刷新、信任变化、cwd 切换与 reload 必须得到对应的新快照，不能把全局永久缓存当作优化。无需求时不加持久缓存、文件 watcher 或后台预热系统。
4. 将查看器在首次打开、PTY 实现在首次启动 PTY、workflow 执行依赖在首次启动 workflow 时加载。注册描述、schema、必要原生 renderer 和首次补全仍须及时就绪；异步边界扩展现有模块入口，遵循 Pi 的加载与注册契约。首次使用的耗时必须同时测量，避免将全部启动等待转移给第一个命令。
5. 根据真正独立的读取关系减少串行等待；不得仅将初始化丢到后台后宣称启动完成。tasks、队列配置、活动执行恢复、调度处理、工具说明及 RPC 在允许用户/模型调用前满足既有就绪契约，异步刷新受到绑定代次约束。

不改变进程级 jobs/agents/workflow owner 在 reload/new/resume/fork/tree 中的保活与 quit 清理。部分模块关闭仍可能需要既有 owner 查询或级联停止；减少初始化不得丢失这些跨模块契约，也不能靠禁用现有功能获取性能改善。Pi 的真实 TypeScript 加载与 reload 隔离行为需随按需导入验证，不直接修改宿主私有 loader。

## 实测结论

Linux、Node 24.22.2、Pi 1.5.0，同一工作目录与配置，使用公开 DefaultResourceLoader 的真实 TypeScript 路径及 createAgentSession/bindExtensions；离线模型，无 tmux、其他扩展和网络请求。双方各预热一次转换缓存，再交替采样五个独立 Node 进程，记录中位数。ready 包含扩展加载、会话创建与首次绑定，不包含 Node/Pi 自身模块导入或 CLI 终端探测。

| 场景 | 优化前 ready | 优化后 ready | 优化前 /reload | 优化后 /reload |
| --- | --- | --- | --- | --- |
| 默认模块、空自定义资源 | 229.1ms | 195.5ms（约 15%） | 111.5ms | 97.7ms |
| 全部业务模块关闭 | 208.9ms | 81.7ms（约 61%） | 92.8ms | 66.6ms |
| 默认模块、60 个自定义类型 | 265.7ms | 220.8ms（约 17%） | 139.8ms | 104.9ms |

默认场景扩展加载阶段由 174.3ms 降为 27.0ms，部分注册成本移入绑定，总就绪仍降低；首次打开列表约 20ms，包含按需加载和新增 BrowserView 初始化。默认 ready 取样范围为 224.6–230.9ms 与 194.4–204.1ms；资源场景为 262.2–288.9ms 与 214.7–402.5ms，后者存在一次明显离群值，因此仅以中位数描述。数字不代表用户 SSH/tmux 下完整 CLI 启动时长，也不承诺其他设备相同比例。

真实 Pi CLI 的首次 PTY 后端加载、生成/工具/压缩退出清理，以及 SDK 的首次子代理、workflow、询问、reload/会话切换检查通过。Jiti 并发共享图会暴露未完成导出，注册导入采用顺序加载，首次并发执行共享 Promise。

## 验收

- 在同一目标环境提供前后启动差值和阶段贡献，确认瓶颈阶段改善且整体启动改善；具体预算由基线和用户实际等待体验确定。
- 默认启动后所有启用入口、首次 `@类型` 补全和首次工具调用正确；关闭模块不执行其非必要发现/加载。空资源与较多实际资源均不出现重复全量扫描。
- 首次打开列表、启动 pipe/PTY、启动 child/workflow 的延迟可接受；运行中 reload、切换 cwd/会话与退出保留 owner、通知、控制和清理行为。
- 配置错误、资源损坏及加载失败仍能在应当处理的边界报告，不因性能优化静默忽略。

优先复用已有模块准入、资源发现和生命周期检查，只为加载顺序及快照失效等明确跨模块风险调整必要验证。稳定的加载边界与刷新规则在实施后局部更新 [公共运行时](../../../current/runtime/index.md)、[类型与资源](../../../current/agents/resources.md) 和 [验证规则](../../../current/validation.md)；基准结论及适用范围归入 `doc/finished`，不记录本机临时产物或测试流水账。
